Digital Time Attendance System

A web + mobile-friendly app where staff log in, clock in and out, and admins see who is currently onsite. Data is stored in Google Sheets, accessed only through a secure backend.

Sprint 1 (S1) Frontend: React Backend: Node.js + Express Auth: Firebase Data: Google Sheets API

The brief in plain English

  • What it is: A time-attendance app. Staff sign in with email + password, then clock in when they arrive and clock out when they leave. Admins see a live dashboard of who is IN and who is OUT.
  • Two roles: Staff can only do their own check-in/out. Admins get the live dashboard, settings and control over all staff. This is enforced on the backend (API) and the UI.
  • How attendance is captured: Either a button on screen (clock in / clock out) or by scanning a QR code at the entrance with the phone camera.
  • Where data lives: A Google Sheet, which the backend reads and writes. The frontend never touches Google Sheets directly, and secrets are never exposed to the browser.
  • Rules that protect the data: The server (not the phone) stamps the time, and duplicate clock-ins/clock-outs are rejected.
  • UX expectation: Every action gives clear feedback — loading, success and friendly error messages (no technical errors shown to users).
  • Works everywhere: Mobile and desktop. The QR scanner needs a secure (HTTPS) connection to use the camera.

How the work is split

Frontend (React)

Project setup, login page, app layout, clock in/out screens, attendance status, QR scanner UI, admin dashboard, loading/error states.

Backend (Node/Express)

Server + routes, Google Sheets integration, Firebase auth checks, clock in/out endpoints, QR validation, duplicate prevention, RBAC.

Design (Figma)

Key concepts explained

Acceptance Criteria

The checklist that says "this ticket is built correctly." Every bullet must be true before the ticket is accepted.

Definition of Done (DoD)

The wider quality bar: code reviewed + merged, tests passing, deployed to staging, verified by the Product Owner, docs written.

RBAC (Role-Based Access Control)

Staff vs Admin. Admins see everything; staff only see their own check-in/out. Enforced in the API (403 Forbidden) and hidden in the UI.

Firebase Auth

Handles login and issues a token. The backend verifies that token on protected endpoints (401 if invalid).

Google Sheets as the database

Attendance rows live in a spreadsheet. Only the backend writes to it via a secure service account. Credentials stay in .env.

Staging

A live-but-test copy of the app where features are verified before going further. Needed for QR camera testing (HTTPS).

S1-11b Create API endpoint for QR code validation and check-in Backend Due 18 Nov

Second half of S1-11: server-side validation and secure logging of QR check-ins.

Acceptance criteria
  • Express endpoint (e.g. POST /api/attendance/qr-checkin) receives the QR payload.
  • Verifies the Firebase token (401 if invalid).
  • Validates the QR against the expected building/location ID (400 if invalid).
  • Writes a row with User ID + server-generated timestamp.
  • Returns 200 OK on success.
  • Invalid QR codes write nothing to the Sheet.
Definition of done
  • API contract documented and shared (Postman/Swagger).
  • Rejects missing/invalid tokens (verified in Postman/ThunderClient).
  • Timestamp generated server-side; row aligns with existing column headers.
  • Correct status codes (200/400/401/500); no stack traces leaked.
  • Unit/integration tests cover happy + sad paths; merged and deployed to staging.
S1-12 Prevent duplicate clock-ins and clock-outs Backend Due 17 Nov

Stop double taps, double scans and slow-connection retries from corrupting the Sheet.

Acceptance criteria
  • Clock-in rejected if the latest action is already "Clock In".
  • Clock-out rejected if the latest action is already "Clock Out", or if there is no clock-in yet.
  • A rejected request saves nothing to the Sheet.
  • A rejected request returns a clear message, e.g. "You are already clocked in".
  • Two identical entries sent at the same time save only one.
  • A valid first clock-in and first clock-out still save correctly.
Definition of done
  • Duplicate checks added for both clock-in and clock-out.
  • All acceptance criteria tested and passing.

Out of scope: showing the message on screen, staff login, admin editing past entries. Agree error wording with the frontend dev.

S1-16 Implement basic loading and error messages Frontend + Design Due 17 Nov

Type: Feature/UI · Priority: Medium · ~2 days. Reusable loading/success/error states for login, clock in/out and dashboard.

Acceptance criteria
  • Loading indicator during login, clock-in/out and dashboard requests.
  • Buttons disabled while loading (no double submits).
  • Success message only after the server confirms.
  • Failed login: "Email or password is incorrect." (don't say which is wrong).
  • 401 → message + redirect to login. 403 → "You don't have access to this page."
  • 409 duplicate → "You're already clocked in." 500 → "Something went wrong. Please try again."
  • Offline → "You're offline. Check your connection and try again."
  • Failed data loads show a "Try again" button.
  • Never show raw errors, status codes or stack traces.
  • Readable on mobile; errors use icon/text, not colour alone.
  • Components reusable, not hard-coded to one screen.
Definition of done
  • Design approved by PO before development.
  • Every case triggered and checked; verified on phone + desktop.
  • No technical/sensitive data in messages; components documented.
  • Reviewed, merged, deployed to staging, verified by PO.

Out of scope: automatic/safe retries, offline mode or queuing, full responsiveness, full a11y audit, logging/monitoring, full-page skeletons, translations.
